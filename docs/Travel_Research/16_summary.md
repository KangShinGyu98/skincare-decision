# 16 Summary: 유입부터 사용 전과정 요약

_Execution summary document | Claude | 2026-08-19_

---

## 1. 이 서비스가 풀어야 하는 한 문장

> **"지금 내 조건에서 무엇을 먼저 결정해야 하는지, 무엇은 아직 결정하지 않아도 되는지 줄여주고, 만든 계획이 실행 가능한지 검증해주는 서비스."**

핵심은 `더 많은 추천`이 아니라 `더 적은 결정`이다.
그리고 그 시작점은 여행 취향 설문이 아니라 **`Decision Gate`(결정 상태 점검)**다.

---

## 2. 사용자 분류

이 서비스의 실전 세그먼트는 아래 3개 + 보조 1개가 가장 적절하다.

### A. 어디로 갈지부터 막힌 사람

특징:

- 날짜(연차)는 있는데 목적지가 없다
- 여행지 추천 콘텐츠를 볼수록 더 헷갈린다
- 동행과 "어디 갈까"만 반복하고 있다

이 사람이 원하는 것:

- 조건(날짜·예산·동행) 기반 후보 축소
- 이 시기에 피해야 할 곳부터 거르기
- 후보 2~3개의 비교 기준

핵심 기능:

- `Trip Frame 입력`
- `Destination Decision Card`

### B. 목적지는 정했는데 뭐부터 해야 할지 모르는 사람

특징:

- "오사카 가기로 했어요. 근데 이제 뭐 하죠?"
- 항공·숙소·일정을 동시에 붙잡고 아무것도 확정 못 한다
- 특가 알림에 흔들린다

이 사람이 원하는 것:

- 지금 결정할 것 1가지
- 결정 데드라인 타임라인
- 각 결정의 판단 기준

핵심 기능:

- `Decision Gate`
- `Decision Timeline`
- `Decision Card`

### C. 예약은 끝났고 일정을 짜야 하는 사람

특징:

- `오사카 3박 4일 일정` 검색으로 들어온다
- 저장해 둔 장소가 수십 개인데 조립을 못 한다
- AI로 일정을 뽑아봤지만 믿지 못한다

이 사람이 원하는 것:

- 빠른 일정 구성 진입
- 일정의 현실성 검증 (이동시간·휴무·체력)
- 필수/선택 우선순위 정리

핵심 기능:

- `일정 fast lane`
- `Day Plan + Priority Tag`
- `Reality Check`

### D. 보조 세그먼트: 지난 여행 복기형

특징:

- 지난 여행에서 뭔가 아쉬웠는데 정확히 무엇이 문제였는지 모른다
- 같은 실수(과밀 일정, 숙소 위치)를 반복한다

이 사람이 원하는 것:

- 실패 요인 정리
- 다음 여행에 적용할 회피 규칙

핵심 기능:

- `Trip Debrief`
- `Trip Postmortem`

## 3. 유입부터 사용까지 전체 흐름

```text
콘텐츠/검색 유입
-> 진입 분기 (A/B/C/D)
-> Trip Snapshot (조건·확정 상태 입력)
-> Decision Gate
-> Decision Result + Timeline
-> Decision Matrix (결정 유형별 기준 + 후보)
-> Day Plan + Reality Check
-> 여행 중 재조정 / 여행 후 Debrief
```

핵심 설계 원칙은 3가지다.

1. `취향 프로필보다 결정 상태 점검이 먼저` 온다 (Gate-first)
2. `이미 목적지·예약이 확정된 사람`을 위한 fast lane이 있다 (C 세그먼트)
3. 결정 기준과 후보 비교는 `Decision Matrix`로 한 화면에서 본다

---

## 3-1. 유입

현실적인 유입 채널은 4개다.

1. 검색 유입
   예: `오사카 3박4일 일정`, `항공권 언제 사야`, `다낭 우기`, `아이랑 도쿄 숙소 위치`

2. 판단형 콘텐츠 유입
   예: "항공권부터 사면 안 되는 3가지 경우", "오사카에서 빼야 할 것부터 정하는 법"

3. 계산기/체크리스트 유입
   예: "내 일정 과밀도 체크", "지금 예약 vs 대기 판단기"

4. AI 일정 검증 유입
   예: "ChatGPT가 짜준 일정, 진짜 가능한지 검증하기"

---

## 3-2. 진입 분기

유입 직후 첫 질문은 복잡하면 안 된다.

추천 진입 버튼:

1. 어디로 갈지부터 정하고 싶어요
2. 목적지는 정했는데 뭐부터 할지 모르겠어요
3. 예약은 끝났고 일정을 짜야 해요
4. 지난 여행이 왜 아쉬웠는지 알고 싶어요

3번 사용자는 목적지 preset(오사카·도쿄·후쿠오카·다낭·방콕)을 바로 받는다.

---

## 3-3. Stage 1: Trip Snapshot

개인화 설문이 아니라 현재 상태 입력이다. 1분 안에 끝나야 한다.

권장 입력:

- 날짜: 확정 / 유동 (몇 박)
- 동행: 혼자 / 커플 / 친구 / 아이 동반 / 부모님 동반
- 예산대
- 확정된 것 체크: 목적지 / 항공 / 숙소 / 일정
- (선택) 여행 목적: 휴식 / 경험 / 기념

여기서 중요한 점:

- 취향(음식/자연/쇼핑)은 초기 필수값이 아니다
- `확정 상태`와 `동행`, `날짜 유연성`이 판단에 더 먼저 필요하다

---

## 3-4. Stage 2: Decision Gate

초기 MVP에서 가장 중요한 단계다.

이 단계의 목적은:

- 지금 무엇을 결정할 차례인지 판정
- 순서를 건너뛰고 있으면 경고 (예: 숙소 지역도 없이 개별 호텔 비교 중)
- 이미 늦은 결정이 있으면 우선 처리 지시

### 판정에 쓰는 신호 예시

- 출발까지 남은 기간 × 성수기 여부
- 확정 상태의 조합 (목적지 O, 항공 X, 숙소 X → 항공 우선)
- 날짜 유연성 (유동적이면 항공 타이밍 판단이 달라짐)
- 동행 구성 (아이 동반이면 숙소 지역 기준 강화)

---

## 3-5. Stage 3: Decision Result + Timeline

이 화면에서 사용자에게 아래를 동시에 보여줘야 한다.

- 지금 결정할 것 1가지
- 미뤄도 되는 것과 그 시한 (Decision Timeline)
- 왜 그런지 설명
- 다음 액션 CTA

예시:

- 지금 결정: 항공 (연휴 성수기, 선택지 축소 중)
- 이번 주 안에: 숙소 지역
- 미뤄도 됨: 일별 일정 (D-14 이후), 식당 예약 (D-14부터)
- 이유: 연휴 수요는 공급이 고정된 항공에 먼저 반영된다

핵심은 `추천`보다 `미뤄도 된다`는 판정의 설득력이다. 결정을 줄여주는 경험이 여기서 만들어진다.

---

## 3-6. Stage 4: Decision Matrix

결정 유형별 판단 기준과 후보 비교를 한 화면에서 본다.

이 화면에서 동시에 보여줘야 하는 것:

- 이 결정에서 중요한 판단 축 (Decision Card)
- Good fit / Skip if
- 내 조건으로 필터링된 후보 (목적지 2~3개, 숙소 지역 3~5개 수준)
- 유사 여행자 증거 (있는 경우)
- 후보별 적합/주의 태그

예: 숙소 지역 결정이라면 — 동선 중심성, 공항 접근, 밤 편의, 짐 동선 기준과 함께 우메다/난바/텐노지를 내 조건 기준으로 비교한다. 개별 호텔 비교는 지역 확정 이후로 미룬다.

---

## 3-7. Stage 5: Day Plan + Reality Check

일정 구성과 검증이 붙어 있는 화면이다.

- 장소를 담을 때마다 Priority Tag (필수/선택/대안)를 붙인다
- AI 생성 일정이나 직접 짠 일정을 붙여넣으면 파싱해서 검증한다
- 판정: 하루 이동 총량, 영업시간·휴무 충돌, 동행 보정 체력, 예약 데드라인
- 수정 제안: "선택 태그 1곳 제거", "이 스팟은 Day 3 오전으로 이동"

이 화면이 AI 생성 도구들과의 관계를 정의한다. 생성은 어디서 하든 좋다. 검증은 여기서 한다.

---

## 3-8. Stage 6: 여행 중 재조정과 여행 후 기록

차별화와 리텐션은 여기서 생긴다.

여행 중:

- 계획이 깨졌을 때(비·휴무·체력) Priority Tag 기반 재조정: 필수는 지키고 선택을 버리고 대안을 꺼낸다

여행 후:

- 5분 Debrief 체크인: 실행률, 최고/최악, 실패 요인 태그
- Postmortem: 반복 패턴 감지 → 다음 여행 규칙 제안 → 사용자 승인
- 구조화 후기 1건 작성 유도 → Similar-Traveler 데이터 축적

재방문 시 기대되는 변화:

- 다음 여행의 Trip Snapshot이 미리 채워져 있음
- 회피 규칙이 Priority 판단에 반영됨
- 판단이 점점 개인화되고 보수적으로 정확해짐

## 4. 현실적/법적 실현 가능성

## 4-1. 현실적 실현 가능성

### 결론

**높다.**
단, `웹 우선 + 목적지 5곳 + 룰 기반 판단 + 수동 시딩` 범위로 시작해야 한다.

### 왜 가능한가

- 한국 사용자는 이미 트리플·AI 플래너로 조건 입력형 여행 UI에 익숙하다
- MVP는 ML 모델보다 `구조화된 질문`, `결정 룰셋`, `정리된 판단 카드`가 더 중요하다
- 이동시간·영업시간은 지도 API 참조로 해결 가능해 자체 POI DB가 필요 없다
- 처음부터 전 세계를 다룰 필요가 없다

### 현실적으로 어려운 부분

- 결정 룰셋(성수기 × 확정 상태 × 동행)의 품질 설계와 유지
- Reality Check의 동행 보정 기준선을 설득력 있게 만드는 것
- 유사 여행자 후기를 구조화해서 모으는 콜드스타트
- `추천`보다 `보류`를 설득하는 UX
- 여행 후 Debrief의 기록 동기 설계

## 4-2. 법적/규제 경계 (전문 검토 필요 항목)

### 결론

**정보 기반 여행 의사결정 보조 서비스로는 부담이 낮은 편이다.**
다만 아래 선을 넘는 순간 요건이 달라지므로, MVP 범위 확정 시 법무 검토가 필요하다.

### 가능한 영역 (낮은 부담)

- 여행 결정 기준·판단 정보 제공
- 일정 검증과 우선순위 제안
- 구조화 후기 수집·표시
- 외부 예약 서비스로의 단순 링크

### 검토가 필요해지는 영역

1. **여행업 등록:** 항공·숙박 등의 예약을 직접 대행·알선하거나 수수료를 받는 구조로 가면 관광진흥법상 여행업 등록 요건 검토가 필요하다. MVP는 판단 제공 + 외부 링크로 시작해 이 부담을 피한다.
2. **가격·시기 관련 확정 표현:** "지금 사면 무조건 이득" 같은 보증성 표현은 소비자 오인 리스크가 있다. 조건부 판단 언어를 유지한다.
3. **위치·개인정보:** 여행 이력, 동행 구성(아동 포함), 위치 기반 기능은 개인정보·위치정보 규제 관점에서 보수적으로 설계한다.
4. **협찬·광고 구분:** 제휴 링크와 판단 결과를 분리하고, 대가성 콘텐츠는 명확히 표시한다.

### 실무 가드레일

- `보장`, `확정`, `무조건` 대신 `권장`, `기준`, `조건부 판단` 언어 사용
- 예약·결제는 외부 서비스로 연결하고 자체 처리하지 않는다 (MVP 기준)
- 현지 변동(휴무·날씨·혼잡) 리스크 고지를 결과 화면에 상시 노출

## 5. 어디까지 구현해야 하나

### 추천 결론

**웹 우선, 모바일 퍼스트, Reality Check까지는 해야 한다. 앱은 나중이다.**

왜냐하면:

- 초기 유입은 검색과 판단형 콘텐츠가 중심이다
- 앱 설치 전에 가치를 증명해야 한다
- 여행 계획은 데스크톱+모바일 웹 혼용 시나리오가 많다 (엑셀 대체 맥락)

### MVP 범위

해야 하는 것:

- 4개 진입 버튼과 목적지 preset fast lane
- `Trip Snapshot`
- `Decision Gate` + `Decision Result + Timeline`
- `Decision Matrix` (목적지·항공·숙소 지역)
- `Day Plan + Priority Tag`
- `Reality Check v1` (이동시간 합산 + 휴무 충돌 + 동행 보정)
- `Trip Debrief Lite`

나중에 해도 되는 것:

- 네이티브 앱
- 목적지 확장 (5곳 이후)
- 동행 합의 공유 뷰
- Similar-Traveler 만족률 노출 (데이터 축적 후)
- 예약 제휴 연동

### 후보 추천은 어디까지?

**해야 한다.**
다만 `무한 리스트`가 아니라 아래 정도면 충분하다.

- 목적지 후보 2~3개 / 숙소 지역 후보 3~5개 수준의 shortlist
- 각 후보의 적합/주의 이유 설명
- 개별 호텔·항공편 비교는 외부(메타서치·OTA) 링크로 위임

즉, `추천 리스트`가 아니라 `필터링된 Decision Matrix`여야 한다.

## 7. 구현 수준 제안

### Level 0: 개념 검증용 프로토타입

- 목적지 1곳 (오사카)
- Trip Snapshot + Decision Gate + Decision Result 중심
- Decision Matrix는 샘플 수준, Reality Check는 수동 데모
- 사용자 테스트 목적

### Level 1: 현실적 MVP

- 목적지 5곳
- Decision Card 25종 수동 시딩
- Decision Timeline
- Reality Check v1 (지도 API 연동)
- Trip Debrief Lite
- 모바일 웹

### Level 2: 첫 상용 버전

- 유사 여행자 구조화 후기 축적·노출
- Postmortem 규칙 엔진
- 계정 기반 저장·다음 여행 이월
- 동행 공유 뷰
- 검색 유입 최적화

## 8. 실제 사용 예시 및 시나리오

### 시나리오 1. "목적지는 정했는데 뭐부터 할지 모르는" 사용자

사용자:

- 31세, 10월 연휴 오사카 3박 4일, 커플
- 항공·숙소 미정, 인스타 저장만 40개

유입:

- 검색: `오사카 여행 준비 순서`

서비스 흐름:

1. `목적지는 정했는데 뭐부터 할지 모르겠어요` 선택
2. Trip Snapshot: 날짜 확정, 커플, 중간 예산, 목적지만 확정
3. Decision Gate: 연휴 성수기 + 항공 미확정 감지
4. Decision Result: `지금 결정: 항공. 숙소는 지역만 이번 주에. 일정은 D-14 이후`
5. Decision Matrix에서 항공 판단 기준(시간대 가치·취소 규정) 확인
6. 다음 방문 시 숙소 지역 Matrix로 이어짐

핵심 가치:

- 모든 것을 동시에 붙잡던 상태에서 `지금 하나`로 축소

### 시나리오 2. "예약 끝, 일정만 남은" 사용자

사용자:

- 27세, 친구 2명과 도쿄 3박 4일, 항공·숙소 확정
- ChatGPT로 일정 초안을 뽑아둠

유입:

- 검색: `도쿄 일정 검증`, 콘텐츠: "AI 일정 그대로 가면 생기는 일"

서비스 흐름:

1. `예약은 끝났고 일정을 짜야 해요` 선택 → 도쿄 preset
2. 일정 초안 붙여넣기
3. Reality Check: Day 2 과밀 판정 (이동 6회, 도보 13km), 시부야→아사쿠사→오다이바 동선 비효율, 월요일 휴무 스팟 감지
4. 수정 제안 적용 + 필수/선택 태그 정리
5. 공유 링크로 친구들에게 판정 근거와 함께 전달

핵심 가치:

- "AI가 짜준 일정"이 "검증된 일정"으로 바뀜, 동행 설득 근거 확보

### 시나리오 3. "어디로 갈지부터 막힌" 사용자

사용자:

- 38세, 아이(5세) 동반, 12월 초 4일, 첫 가족 해외여행

유입:

- 검색: `12월 아이랑 해외여행 어디`

서비스 흐름:

1. `어디로 갈지부터 정하고 싶어요` 선택
2. Trip Snapshot: 12월 초, 아이 동반, 4일, 중간 예산
3. Destination Decision Matrix: 후보 축소 — 방콕(건기 시작, 직항 5.5시간, 아이 동반 부담 중간), 오사카(온화, 2시간 미만, 유아차 환경 좋음) 비교. 다낭은 우기 끝물로 주의 표시
4. 유사 여행자 증거: 아이 동반 12월 여행자의 만족 이유 확인
5. 오사카 확정 → 자동으로 B 세그먼트 흐름(순서 판단)으로 이어짐

핵심 가치:

- 후보를 늘리는 추천이 아니라 조건으로 걸러진 2~3개 비교

### 시나리오 4. 지난 여행 복기형 사용자

사용자:

- 지난 후쿠오카 여행이 어딘가 아쉬웠음
- 다음 달 오사카 계획 중

서비스 흐름:

1. `지난 여행이 왜 아쉬웠는지 알고 싶어요` 선택
2. Debrief: 계획 12곳 중 7곳 실행, 실패 태그 — 과밀 일정, 숙소 위치
3. Postmortem: `하루 앵커 2곳 상한`, `역 도보 8분 이내 숙소` 규칙 제안 → 승인
4. 다음 오사카 계획에서 규칙 자동 반영

핵심 가치:

- 실패 경험이 다음 결정의 입력이 됨

2. `미뤄도 된다`는 판정이 설득력 있게 작동하는가 (결정 축소 체감)
3. Reality Check 판정 후 실제로 일정을 수정하는가
4. 여행 후 기록이 다음 여행 계획으로 이어지는가
