# 17 Wireframe: 화면 구성 및 컴포넌트 정의

_Wireframe planning document | Claude | 2026-08-19_

---

## 1. 문서 목적

이 문서는 `16_summary.md` 기준으로 **Travel Decision MVP의 화면 구조와 화면별 핵심 컴포넌트**를 정리한 와이어프레임 문서다.

이 설계의 핵심은 아래 4가지다.

1. **Decision Gate가 취향 프로필보다 먼저 오는 구조**
2. **목적지·예약 확정 사용자를 위한 fast lane 제공**
3. **결정 기준과 후보 비교를 Decision Matrix로 통합**
4. **일정 구성과 Reality Check를 한 화면에 결합**

---

## 2. 화면 수 결론

### MVP 기준

**코어 화면 8개**가 적절하다.

1. 랜딩 / Intent Entry
2. 진입 분기 / 세그먼트 선택
3. Trip Snapshot 입력
4. Decision Gate
5. Decision Result + Timeline
6. Decision Matrix
7. Day Plan + Reality Check
8. Trip Debrief / Postmortem

### 선택 화면

운영 편의와 재방문을 위해 아래 **보조 화면 3개**를 붙일 수 있다.

9. 로그인 / 저장 유도
10. 내 여행 기록 보기
11. 공유 가능한 결과 페이지 (동행 합의용)

### 실무 기준 결론

- **MVP 라우트 수:** 8개
- **v1 라우트 수:** 11개 내외
- **피그마 프레임 수:** 상태값까지 포함하면 26~34개
- **프론트엔드 재사용 컴포넌트:** 14~18개

화면 수는 적지만 판정·설명 밀도가 높은 구조다.

---

## 3. 전체 흐름

```text
S01 랜딩 / Intent Entry
 -> S02 진입 분기 / 세그먼트 선택
    -> A 어디로 갈지부터 정하고 싶음
       -> S03 Trip Snapshot
       -> S04 Decision Gate
       -> S06 Decision Matrix (목적지)
       -> S05 Decision Result + Timeline
       -> (목적지 확정 후 B 흐름 합류)

    -> B 목적지는 정했는데 순서를 모름
       -> S03 Trip Snapshot
       -> S04 Decision Gate
       -> S05 Decision Result + Timeline
       -> S06 Decision Matrix (항공/숙소 지역)
       -> S07 Day Plan + Reality Check

    -> C 예약 끝, 일정 구성 필요
       -> 목적지 preset
       -> S03 Trip Snapshot (확정 정보 축약 입력)
       -> S07 Day Plan + Reality Check
       -> (필요 시 S06 식당/스팟 기준 참조)

    -> D 지난 여행 복기
       -> S08 Trip Debrief / Postmortem
```

핵심은 아래 순서다.

> **상태 파악 -> 순서 판정 -> 기준 제시 -> 후보 축소 -> 일정 검증 -> 사용 후 학습**

## 4. 화면별 정의

## S01. 랜딩 / Intent Entry

### 역할

검색/콘텐츠 유입 직후 사용자가
`이 서비스가 뭘 해결해주는지`, `어떤 입구로 들어가야 하는지`, `이미 확정된 사람도 바로 들어갈 수 있는지`를 이해하는 화면이다.

### 핵심 컴포넌트

1. **Hero headline** — "여행 계획, 결정할 것부터 줄여드립니다"
2. **한 문장 가치 제안** — 추천이 아니라 결정 순서와 검증
3. **대표 상황 예시 칩** — `10월 오사카 뭐부터?`, `AI 일정 믿어도 돼?`
4. **직접 진입 CTA 묶음** (4 세그먼트)
5. **목적지 fast lane 칩** — 오사카 / 도쿄 / 후쿠오카 / 다낭 / 방콕
6. **샘플 결과 미리보기 카드** — Decision Result 예시 1장
7. **판단 보조 고지 배너** — 보증이 아닌 조건부 판단임을 명시

### 권장 CTA

- `내 여행 상태부터 정리하기`
- `일정 검증만 빠르게 하기`
- `지난 여행 복기하기`

### 화면 메모

- 첫 화면에서 여행지 사진 피드를 보여줄 필요는 없다. 영감 미디어처럼 보이는 순간 포지셔닝이 무너진다.
- 검색 유입 사용자가 `바로 들어갈 길`(fast lane)을 상단에서 인지해야 한다.

---

## S02. 진입 분기 / 세그먼트 선택

### 역할

사용자를 긴 입력으로 보내기 전에
현재 의사결정 상태를 4개 중 하나로 분기시키는 화면이다.

### 핵심 컴포넌트

1. **세그먼트 선택 카드 4종**
2. **각 세그먼트 설명 한 줄**
3. **대표 예시 문장**
4. **progress header**
5. **도움말 링크 또는 FAQ 토글**

### 세그먼트 버튼

1. 어디로 갈지부터 정하고 싶어요
2. 목적지는 정했는데 뭐부터 할지 모르겠어요
3. 예약은 끝났고 일정을 짜야 해요
4. 지난 여행이 왜 아쉬웠는지 알고 싶어요

### 화면 메모

- 로그인보다 먼저 나와야 한다.
- 3번 세그먼트는 `목적지 preset`과 바로 연결되어야 한다.

---

## S03. Trip Snapshot 입력

### 역할

취향 설문이 아니라 이번 여행의 골격 상태를 받아
판정의 입력값을 만드는 화면이다. 1분 안에 끝나야 한다.

### 핵심 컴포넌트

1. **날짜 선택 + 유연성 토글** (확정 / 유동)
2. **동행 구성 칩** (혼자 / 커플 / 친구 / 아이 동반 / 부모님 동반)
3. **예산대 세그먼트**
4. **확정 상태 체크 그룹** — 목적지 / 항공 / 숙소 / 일정 각각 O·X
5. **여행 목적 칩 (선택)** — 휴식 / 경험 / 기념
6. **건너뛰기 / 잘 모르겠어요 버튼**

### 입력 항목

- 날짜와 유연성
- 동행 구성
- 예산대
- 확정 상태 4종
- (선택) 여행 목적

### 화면 메모

- 취향(음식/자연/쇼핑)은 여기서 묻지 않는다. 후보 비교 단계(S06)에서 필요할 때만 묻는다.
- 초기 개인화의 목적은 정교한 추천이 아니라 `판정 정확도`다.

---

## S04. Decision Gate

### 역할

이 서비스의 첫 핵심 판단 화면이다.
사용자에게 `지금 무엇을 결정할 차례인지`, `순서를 건너뛰고 있지 않은지`, `이미 늦은 결정이 있는지`를 점검하게 한다.

### 핵심 컴포넌트

1. **판정 신호 요약 바** — 남은 기간 D-xx, 성수기 여부, 확정 상태
2. **순서 점검 체크리스트** — 현재 하고 있는 행동 확인
3. **즉시 피드백 배너** — 체크 즉시 순서 경고 표시
4. **지연 경고 박스** — 이미 늦은 결정 강조
5. **다음 단계 CTA**

### 순서 점검 문항 예시

- 개별 호텔을 비교하고 있다 (숙소 지역 미정 상태라면 경고)
- 일별 일정을 짜고 있다 (항공 미확정 상태라면 경고)
- 매일 가격만 확인하고 있다 (판단 기준 없는 대기 상태 감지)
- 저장한 장소가 30개 이상이다 (정리 아닌 판단 단계 안내)

### 조건부 문항 예시

아이 동반:

- 낮잠/휴식 시간을 일정에 반영할 계획이다
- 유아차 이동 구간을 확인했다

성수기 출발:

- 취소 무료 옵션의 마감일을 알고 있다

### 화면 메모

- 이 화면은 설문이 아니라 `gate`여야 한다.
- 사용자는 여기서 이미 "지금 하지 말아야 할 것"을 일부 이해해야 한다.

---

## S05. Decision Result + Timeline

### 역할

사용자에게 `지금 결정할 것`, `미뤄도 되는 것과 시한`, `왜 그런지`, `다음 행동`을 동시에 보여주는 허브 화면이다.

### 핵심 컴포넌트

1. **Now Decision Card** — 지금 결정할 것 1가지
2. **Decision Timeline** — 출발일 역산 데드라인 바 (항공/숙소/예약/일정)
3. **보류 Card** — 미뤄도 되는 것 + 근거
4. **왜 이런 결론이 나왔는지 설명 블록**
5. **다음 액션 CTA 묶음**
6. **지연 경고 배너** (해당 시)
7. **결과 공유 버튼** (동행 합의용)

### 결과 예시

- 지금 결정: 항공 (연휴 성수기, 선택지 축소 중)
- 이번 주 안에: 숙소 지역
- 미뤄도 됨: 일별 일정 (D-14 이후), 식당 예약 (D-14부터)
- 이유: 연휴 수요는 공급이 고정된 항공에 먼저 반영됨

### 권장 CTA

- `항공 판단 기준 보기`
- `숙소 지역 비교하기`
- `타임라인 저장하기`

### 화면 메모

- 이 화면의 설득력이 MVP 성패를 좌우한다.
- "추천"보다 "왜 이건 아직 안 해도 되는지"의 설명이 더 중요하다.

---

## S06. Decision Matrix

### 역할

결정 유형별 판단 기준(Decision Card)과 내 조건으로 필터링된 후보 비교를 한 화면에서 보여준다.
목적지 비교, 항공 기준, 숙소 지역 비교가 이 화면의 변형으로 구현된다.

### 핵심 컴포넌트

1. **현재 결정/조건 요약 바**
2. **결정 유형 헤더** (목적지 / 항공 / 숙소 지역)
3. **핵심 판단축 블록** (Decision Card)
4. **Good fit / Skip if 비교 블록**
5. **필터링된 후보 Matrix** (2~5개)
6. **후보별 적합/주의 태그**
7. **Similar-Traveler Evidence 블록** (데이터 있는 경우)
8. **비교 기준 커스터마이즈 컨트롤**
9. **외부 링크 분리 영역** (메타서치/OTA — 판단 영역과 시각 분리)
10. **다음 단계 CTA**

### 결정 유형별 예시 모듈

- 목적지: 시기 적합성, 예산 레벨, 비행 강도, 동행 적합성
- 항공: 시간대 가치, 경유 리스크, 취소 규정, 타이밍 가이드
- 숙소 지역: 동선 중심성, 공항 접근, 밤 편의, 짐 동선

### 후보 Matrix 기준 예시

- 내 조건 기준 적합도 태그 (适합 / 조건부 / 주의)
- 조건별 트레이드오프 한 줄 요약
- 유사 여행자 만족 신호 (있는 경우)

### 화면 메모

- 이 화면이 이 서비스의 실질적인 `탐색 코어`다.
- 개별 호텔·항공편 리스트를 직접 보여주지 않는다. 그 단계는 외부 서비스에 위임하고, 여기서는 `무엇을 봐야 하는지`와 `어느 후보군인지`까지만 좁힌다.

---

## S07. Day Plan + Reality Check

### 역할

일정 구성과 검증이 결합된 화면이다.
직접 구성하든 AI 초안을 가져오든, 모든 일정은 검증을 거쳐 확정된다.

### 핵심 컴포넌트

1. **일자 탭 / 타임라인 보드**
2. **장소 추가 + Priority Tag 선택** (필수 / 선택 / 대안)
3. **AI/텍스트 일정 가져오기 모듈** (붙여넣기 → 파싱)
4. **Reality Check 판정 카드** — 하루 단위 판정 (여유 / 적정 / 과밀)
5. **판정 근거 블록** — 이동 총량, 휴무 충돌, 동행 보정 기준
6. **수정 제안 카드** — 제거/이동/대체 제안 + 원탭 적용
7. **예약 데드라인 알림 칩**
8. **우천/체력 대안 슬롯 표시**
9. **일정 공유 CTA** (판정 근거 포함)

### Reality Check 판정 예시

- 판정: Day 2 과밀 (아이 동반 기준)
- 근거: 도보 11.4km(권장 7km), 이동 5회(권장 4회), 15:00 A스팟 화요일 휴무
- 제안: `선택` 태그 C 제거, A는 Day 3 오전 이동, 우천 대안 D 등록

### 화면 메모

- 생성 기능을 내장하지 않는다. `가져오기 + 검증`이 이 화면의 정체성이다.
- 판정에는 반드시 기준(왜 과밀인지)이 붙어야 한다. 점수만 보여주면 신뢰가 생기지 않는다.

---

## S08. Trip Debrief / Postmortem

### 역할

이 화면은 두 개의 서브플로우를 가진다.

- **Debrief 탭:** 이번 여행의 계획 대비 실제 5분 기록
- **Postmortem 탭:** 반복 실패 패턴에서 다음 여행 회피 규칙 생성

### 핵심 컴포넌트

1. **탭 스위처**
2. **실행률 체크 모듈** — 계획 장소별 방문 여부 탭
3. **최고/최악 선택 픽커**
4. **실패 요인 태그 칩** — 과밀 일정 / 숙소 위치 / 시기 / 예약 실패 / 동행 불일치 / 날씨
5. **다음에 유지할 것 입력**
6. **반복 패턴 감지 카드** (Postmortem)
7. **회피 규칙 제안 카드** — 승인 / 수정 / 무시
8. **구조화 후기 작성 유도 모듈** (조건 메타데이터 포함)
9. **기록 저장 CTA**

### Postmortem 결과 예시

- 반복 패턴: 2회 연속 `과밀 일정`, 숙소-일정 평균 이동 38분
- 규칙 제안: 하루 앵커 2곳 상한 / 역 도보 8분 이내 숙소
- 원칙: 원인 `후보`로 표현, 사용자 승인 후에만 적용

### 화면 메모

- 여행 종료 시점 알림에서 바로 진입되어야 한다. 5분 이내 완료가 목표다.
- D세그먼트 사용자는 이 화면에서 바로 시작할 수 있어야 한다.

## 5. 보조 화면

## S09. 로그인 / 저장 유도

### 목적

첫 방문 때 막는 화면이 아니라, 결과(타임라인·검증된 일정)를 본 뒤 저장이 필요할 때 등장하는 화면이다.

### 핵심 컴포넌트

1. 결과 저장 안내
2. 소셜 로그인 버튼
3. 저장 시 얻는 이점 요약 (타임라인 알림, 다음 여행 이월)
4. 나중에 하기 버튼

---

## S10. 내 여행 기록 보기

### 목적

과거 여행, 판정 결과, 회피 규칙, 다가오는 데드라인을 다시 보는 화면이다.

### 핵심 컴포넌트

1. 진행 중 여행 카드 (타임라인 D-day 표시)
2. 과거 여행 타임라인
3. 내 회피 규칙 묶음
4. 재탐색 CTA

## 7. 구현 정밀도 기준

### 디자인 기준

로우파이 와이어프레임은 8~11화면이지만, 실제 설계에서는 아래 상태를 같이 잡아야 한다.

- 기본 상태
- 선택 상태
- 로딩 상태 (Reality Check 판정 중)
- 결과 없음 상태 (데이터 없는 목적지)
- 입력 누락 상태
- 순서 경고 / 지연 경고 노출 상태
- 판정 결과별 상태 (여유 / 적정 / 과밀)

따라서 실제 피그마 프레임은 **최소 26개 이상**으로 보는 것이 안전하다.

### 프론트엔드 기준

개발 단위로 보면 다음 정도가 현실적이다.

- **페이지 컴포넌트:** 8~11개
- **재사용 컴포넌트:** 14~18개
- **화면 전용 모듈:** 6~9개
- **총 UI 단위:** 24~30개

즉, 작아 보이지만 3~4페이지짜리 단순 서비스는 아니다. 특히 S07(Day Plan + Reality Check)은 단일 화면 중 밀도가 가장 높다.

## 8. 우선 제작 순서

### Phase 1

반드시 먼저 그릴 화면:

1. S01 랜딩 / Intent Entry
2. S02 진입 분기
3. S03 Trip Snapshot
4. S04 Decision Gate
5. S05 Decision Result + Timeline

이 5개만 있어도 제품의 핵심 가치(결정 축소) 검증이 가능하다.

### Phase 2

다음으로 붙일 화면:

6. S06 Decision Matrix
7. S07 Day Plan + Reality Check

이 단계부터 비로소 `후보 축소와 일정 검증까지 되는 서비스`가 된다.

### Phase 3

차별화 강화를 위한 화면:

8. S08 Trip Debrief / Postmortem
9. S11 공유 결과 페이지

이 화면이 들어가면 서비스는 단순 판단 툴이 아니라
`실패 학습과 동행 합의가 가능한 의사결정 플랫폼`으로 바뀐다.

## 9. 최종 권장안

가장 현실적인 설계는 아래와 같다.

- **MVP는 8개 코어 화면**
- **핵심은 S04 Decision Gate + S05 Decision Result + Timeline**
- **탐색 핵심은 S06 Decision Matrix, 검증 핵심은 S07 Reality Check**
- **목적지·예약 확정 사용자를 위한 fast lane을 반드시 제공**
- **외부 예약 링크는 판단 영역과 시각적으로 분리**
- **판정은 항상 근거와 함께, 조건부 언어로 표현**

한 문장으로 정리하면,
**이 서비스의 와이어프레임은 "예쁜 여행지 리스트"를 만드는 작업이 아니라 "상태 파악 -> 순서 판정 -> 기준 제시 -> 후보 축소 -> 일정 검증 -> 사용 후 학습" 흐름을 설계하는 작업이다.**
