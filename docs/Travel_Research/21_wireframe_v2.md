# 21 Wireframe v2: 화면 구성 및 컴포넌트 정의

_Wireframe planning document, rewritten under 18_thesis_revision.md | Claude | 2026-08-19_

> 이 문서는 `17_wireframe.md`를 폐기하고 대체한다.
> 17번의 8개 화면은 전부 출발 전 화면이었다. 새 구조에서 제품의 무게중심은 현장에 있다.

---

## 1. 이 설계의 전제

17번 문서와 가장 크게 달라지는 점은 **화면 수와 설계 노력이 비례하지 않는다**는 것이다.

| 모드 | 화면 수 | 설계 노력 배분 | 이유                                       |
| ---- | ------- | -------------- | ------------------------------------------ |
| Prep | 5개     | 30%            | 관여도 낮음, 실패해도 재시도 가능          |
| Live | 3개     | **60%**        | 서 있는 3초, 실패하면 구글맵으로 영구 이탈 |
| 보조 | 3개     | 10%            | —                                          |

**`L01 지금 뭐하지` 단 한 화면이 제품 전체의 성패를 결정한다.** 이 화면에만 6개 상태가 존재하며, 나머지 모든 화면은 이 화면을 위한 준비이거나 후속이다.

---

## 2. 전체 흐름

```text
[출발 전 · PREP]
P01 변환기 진입 (붙여넣기)
 └→ P02 변환 결과 확인
     └→ P03 플레이북 (엔트리 편집 · 우선순위)
         └→ P04 앵커 등록 (숙소 · 확정 예약)
             └→ P05 준비 완료 + 오프라인 캐시

                        ↓ 여행 시작일 알림

[여행 중 · LIVE]
L01 지금 뭐하지  ←──────────────┐
 ├→ L02 후보 상세 → 구글맵 길찾기 │
 └→ L03 다 별로 → 이유 → 재제시 ─┘

[보조]
X01 동행 플레이북 공유
X02 오늘 기록 (자동)
X03 여행 후 요약
```

핵심 순서는 이렇다.

> **가져오기 → 자동 태깅 → 조건 인덱싱 → (현장) 조건 감지 → 3개 → 기록**

---

## 3. PREP 모드 화면

## P01. 변환기 진입

### 역할

제품의 첫 화면이자 유일한 진입점. 사용자가 이해해야 할 것은 단 하나다. **"이미 저장해둔 걸 여기 붙여넣으면 된다."**

### 핵심 컴포넌트

1. **Hero headline** — "저장만 해둔 40개, 현장에서 못 쓰고 있죠"
2. **붙여넣기 박스 (단일)** — 구글맵 공유 링크 / 일정 텍스트 모두 수용
3. **소스 예시 칩** — 구글맵 저장 / AI 초안 / 블로그 링크 / 일정표
4. **변환 전후 미리보기** — 목록 → 조건별 묶음 시각화
5. **로그인 없이 시작 버튼**

### 화면 메모

- **계획을 세우라고 하지 않는다.** "우리 앱에서 계획하세요"가 등장하는 순간 전환 비용 우회 전략이 무너진다.
- 여행지·날짜 입력을 먼저 요구하지 않는다. 붙여넣은 내용에서 추론한다.
- 이 화면까지가 단독 유입 가치를 가져야 한다.

---

## P02. 변환 결과 확인

### 역할

자동 태깅 결과를 사용자가 한 번에 훑고 승인하는 화면. **개별 편집이 아니라 일괄 확인이 기본 동작**이어야 한다.

### 핵심 컴포넌트

1. **변환 요약 바** — "40개 중 37개 인식, 3개 확인 필요"
2. **확인 필요 항목 우선 노출** — 중복·미인식·위치 모호
3. **엔트리 행 리스트** — 이름 / 카테고리 / 실내외 / 예상 소요
4. **일괄 승인 CTA**
5. **신뢰도 표시 배지** — 확정 / 추정 / 불확실

### 화면 메모

- 37개를 하나씩 확인시키면 사용자는 이탈한다. 기본은 승인이고, 예외만 손댄다.
- 불확실 태그(접근성·대기)는 이 화면에서 **단정하지 않고 출처를 밝힌 문구로** 표시한다.

---

## P03. 플레이북

### 역할

변환된 자산을 조건별 묶음으로 보여주고, 사용자가 최소한의 개입(우선순위·저장 이유)을 하는 화면.

### 핵심 컴포넌트

1. **조건 묶음 뷰** — 비 올 때 / 지칠 때 / 아이 동반 / 짧은 시간
2. **엔트리 카드** — 태그 요약
3. **우선순위 토글** — 필수 / 선택 **2단계만**
4. **저장 이유 입력** — 한 줄, 선택 입력
5. **지역별 분포 미니맵**
6. **커버리지 경고** — "비 올 때 실내 후보가 2개뿐입니다"

### 화면 메모

- **커버리지 경고가 이 화면의 숨은 핵심이다.** 특정 조건의 후보가 부족하면 현장에서 폴백이 자주 발생한다. 출발 전에 이를 알려주는 것이 Prep 모드가 제공하는 유일한 능동적 가치다.
- 일정표 뷰(시간 순 배치)를 제공하지 않는다. 제공하는 순간 사용자는 다시 일정표를 만들고, 그것은 92%의 확률로 무너진다.

---

## P04. 앵커 등록

### 역할

시간 축을 완전히 없애지 않고 **조건 계산의 입력값으로 강등**하는 화면. 숙소와 확정 예약만 등록한다.

### 핵심 컴포넌트

1. 숙소 등록 (위치·체크인/아웃)
2. 확정 예약 등록 (항공·예약 필수 스팟·시간)
3. 앵커 타임라인 (일자별, 아주 단순)
4. 건너뛰기

### 화면 메모

- 여기서 등록된 앵커가 Live 모드의 `남은 시간` 자동 계산 기준이 된다.
- 앵커는 소수여야 한다. 앵커가 많아지면 그것이 곧 일정표다.

---

## P05. 준비 완료 + 오프라인 캐시

### 역할

여행 전 마지막 화면. 오프라인 자산을 내려받고 Live 모드 사용법을 1문장으로 전달한다.

### 핵심 컴포넌트

1. 캐시 다운로드 진행
2. 커버리지 요약 (조건별 후보 수)
3. **Live 모드 예고** — "현지에서 이 버튼 하나만 누르면 됩니다"
4. 동행 공유 CTA
5. 여행 시작일 알림 설정

---

## 4. LIVE 모드 화면

## L01. 지금 뭐하지 — 제품의 핵심 화면

### 역할

서 있는 사용자가 3초 안에 답을 얻는 화면. **열면 이미 답이 있어야 한다.**

### 레이아웃

```
┌─────────────────────────────────┐
│ 비 · 15:20 · 우메다 · 남은 2시간 │ ← 조건 요약 (작게)
├─────────────────────────────────┤
│ [지쳤음] [배고픔] [아이 잠듦]   │ ← 상태 칩 (선택)
├─────────────────────────────────┤
│ ┌─────────────────────────────┐ │
│ │ 한큐 백화점 식품관           │ │
│ │ 도보 6분 · 실내 · 지금 영업  │ │
│ │ 3주 전 저장 "비 오면 여기"   │ │ ← 왜 이것인지
│ └─────────────────────────────┘ │
│ ┌─────────────────────────────┐ │
│ │ 나카자키초 카페 거리         │ │
│ │ 도보 9분 · 실내 · 대기 짧음  │ │
│ │ 오늘 아직 카페 안 감          │ │
│ └─────────────────────────────┘ │
│ ┌─────────────────────────────┐ │
│ │ 우메다 스카이빌딩            │ │
│ │ 도보 11분 · 실내 · 필수 표시 │ │
│ │ 비 와서 전망은 아쉬울 수 있음│ │ ← 정직한 주의
│ └─────────────────────────────┘ │
├─────────────────────────────────┤
│         [ 다 별로 ]              │ ← 하단 고정
└─────────────────────────────────┘
```

### 핵심 컴포넌트

1. **Condition Bar** — 현재 조건 요약 (신뢰의 시작점)
2. **State Chip Row** — 원탭, 안 눌러도 동작
3. **Option Card ×3** — 이름 / 거리·속성 / 상태 / **이유 한 줄**
4. **Status Badge** — 지금 영업 / 대기 짧음 / **저장 안 한 곳**
5. **Reject-All Button** — 하단 고정

### 6개 상태 (이 화면에만)

| 상태            | 처리                                                     |
| --------------- | -------------------------------------------------------- |
| 기본            | 플레이북 후보 3개                                        |
| 후보 부족       | 일반 검색 보충 + **`저장 안 한 곳` 명시 구분**           |
| **후보 0**      | **"지금은 쉬는 게 낫다"** + 숙소 복귀 안내               |
| 오프라인        | 날씨 수동 칩으로 대체, 실시간 정보 숨김                  |
| 위치 권한 없음  | 마지막 위치 기준 + 권한 요청 배너                        |
| 플레이북 없음   | 변환기(P01)로 유도                                       |

### 화면 메모

- **스크롤 금지.** 3개 카드가 화면을 채운다.
- **질문 금지.** 상태 칩은 결과를 좁히는 장치이지 진입 조건이 아니다.
- 이유 한 줄이 없으면 이 화면은 구글맵과 구별되지 않는다.
- 야외 밝은 환경을 전제로 한 명암비, 한 손 조작 탭 타겟.

### 구글맵과의 경계 — 성공 지표의 정확한 정의

카드를 탭해 **길찾기로 구글맵에 넘어가는 것은 이탈이 아니다.** 우리는 `무엇을` 정하고, `어떻게 가는지`는 구글맵이 압도적으로 잘한다. 내비게이션을 만들지 않는다.

19 문서의 핵심 지표 `구글맵 이탈률`은 정확히는 **"선택을 위해 구글맵을 켜는 비율"** 이다. 우리 화면을 보고도 무엇을 할지 다시 검색한다면 그때가 실패다.

---

## L02. 후보 상세

### 역할

카드를 탭했을 때. 결정을 굳히거나 취소하기 위한 최소 정보만 제공한다.

### 핵심 컴포넌트

1. 대표 이미지 1장
2. 핵심 정보 (영업시간·가격대·소요시간)
3. **내가 저장한 맥락** — 출처 링크, 저장 이유, 저장 시점
4. 주의 표시 (불확실 태그는 출처와 함께)
5. **구글맵 길찾기 넘기기 CTA**
6. 목록으로 돌아가기

### 화면 메모

- 리뷰를 길게 붙이지 않는다. 이미 사용자가 저장할 때 검증한 곳이다.
- 이 화면의 목적은 설득이 아니라 **취소 판단**이다. 아니라고 판단할 근거를 빠르게 준다.

---

## L03. 다 별로 → 이유 → 재제시

### 역할

가장 중요한 학습 신호를 마찰 없이 수집한다.

### 핵심 컴포넌트

1. 이유 원탭 3개 — 너무 멀어 / 아까 비슷한 거 함 / 지금 그런 기분 아님
2. **즉시 다른 3개** (추가 질문 없이)
3. 건너뛰기 (이유 없이 재제시)

### 화면 메모

- 오버레이로 처리하고 화면 전환을 만들지 않는다.
- `다 별로` 비율이 높으면 **사용자 문제가 아니라 태깅·필터의 실패**로 해석한다.

## 5. 보조 화면

## X01. 동행 플레이북 공유

동행이 같은 플레이북을 가지면 각자 Live에서 **같은 3개**를 본다. 현장 결정이 대면 대화 3초로 끝난다.

핵심 컴포넌트: 공유 링크 생성 / 참여자 목록 / 각자 필수 표시 병합 / 병합 충돌 표시

**설계 원칙:** 현장에서 메시징·투표를 요구하지 않는다. 같이 서 있는 사람에게 비동기 도구를 쓰게 만드는 것이 협업 플래너들의 실패 지점이다.

## X02. 오늘 기록 (자동)

사용자가 입력하지 않는다. 선택 로그로 자동 생성된다. 반복 회피와 여행 내 학습의 입력이며, 사용자에게는 열람만 제공한다.

## X03. 여행 후 요약

선택 로그 기반 자동 생성. 실제로 간 곳, 안 간 곳, 조건별 선택 패턴. 사용자 입력 부담 0을 원칙으로 한다. (16 문서의 Trip Debrief가 요구했던 5분 기록은 동기 부족으로 실패할 가능성이 높다고 판단해 자동 생성으로 대체한다.)

### 핵심 재사용 컴포넌트 14개

3. **Playbook Entry Card**
4. **Priority Toggle** (필수/선택 2단계)

12. **Reason Line**
13. **Status Badge** (영업/대기/저장 안 한 곳)

### 화면 전용 모듈

1. 변환 전후 미리보기
2. 오프라인 캐시 진행 표시
3. 쉬기 권유 카드 (후보 0 상태)
4. 플레이북 병합 충돌 표시
5. 여행 후 자동 요약 카드

## 7. 구현 정밀도 기준

### 디자인 기준

로우파이 화면은 11개지만 상태를 포함하면 다음과 같다.

- P01~P05: 화면당 2~4 상태 → 약 14 프레임
- **L01: 6 상태 + 칩 조합 변형 → 약 10 프레임**
- L02~L03: 약 5 프레임
- 보조 3화면: 약 6 프레임

**총 피그마 프레임 약 35개**이며, 이 중 L01 계열이 밀도의 3분의 1을 차지한다.

### 프론트엔드 기준

- 페이지 컴포넌트: 8~11개
- 재사용 컴포넌트: 14개
- 화면 전용 모듈: 5~7개
- **추가 요구사항:** 오프라인 캐시 계층, 위치 권한 처리, 백그라운드 위치 기반 체류시간 추정

마지막 항목 때문에 **Live 모드는 순수 웹만으로는 완결되지 않는다.** 16 문서의 "웹 우선, 앱은 나중" 결론은 여기서 수정된다. Prep은 웹, Live는 PWA 또는 네이티브가 현실적이다.

## 8. 우선 제작 순서

### Phase 1 — 핵심 가설 검증

1. P01 변환기 진입
2. P02 변환 결과 확인
3. **L01 기본 상태 + 후보 0 상태**

이 3개 화면만으로 제품의 핵심 가설(현장에서 구글맵 대신 우리를 여는가)을 검증할 수 있다. **여기서 실패하면 나머지를 만들 이유가 없다.**

### Phase 2 — 실사용 가능 수준

4. P03 플레이북 (커버리지 경고 포함)
5. P04 앵커 등록
6. P05 오프라인 캐시
7. L01 전체 상태 + L02 후보 상세

### Phase 3 — 차별화 완성

8. L03 다 별로 루프
9. X01 동행 공유
10. X02·X03 자동 기록·요약

Phase 3이 들어가면 서비스는 단순 검색 도구가 아니라 **현장 선택 데이터를 축적하는 플랫폼**이 된다.

---

## 9. 최종 권장안

- **MVP는 Prep 5 + Live 3 = 8개 코어 화면**
- **설계 노력의 60%는 L01 한 화면에 배분한다**
- **Phase 1은 3개 화면으로 핵심 가설부터 검증한다**
- **일정표 뷰를 어디에도 만들지 않는다** (붕괴하는 구조의 재생산 금지)
- **현장 화면은 스크롤·질문·긴 텍스트를 금지한다**
- **길찾기는 구글맵에 넘긴다** (내비게이션을 만들지 않는다)

한 문장으로 정리하면,
**이 서비스의 와이어프레임은 "여행 계획 화면"을 설계하는 작업이 아니라, 비 오는 오후에 서 있는 사람이 3초 만에 답을 얻는 단 하나의 화면을 설계하고 나머지 전부를 그 화면에 종속시키는 작업이다.**
