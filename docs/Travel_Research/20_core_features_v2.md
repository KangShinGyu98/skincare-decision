## Part 1. 이 제품이 답하는 질문

> **"비 오는 화요일 오후 3시, 아이는 유아차에서 자고, 오전 일정은 40분 밀렸고, 나는 우메다 어딘가에 서 있다. 지금 뭐하지?"**

이 질문에 3초 안에 답하는 것이 제품의 전부다. 나머지 모든 기능은 이 순간을 위한 준비다.

## Part 2. 2-Mode Architecture

```
┌──────────────────────────────────────────────────────────────┐
│  PREP MODE (출발 전, 저관여)                                  │
│  Converter → Auto-Tagger → Playbook → Offline Cache          │
├──────────────────────────────────────────────────────────────┤
│  ── 공유 자산: PLAYBOOK ──                                    │
│  조건 인덱스 옵션 세트 (장소 × 조건 태그)                     │
├──────────────────────────────────────────────────────────────┤
│  LIVE MODE (여행 중, 고관여)                                  │
│  Context Sensor → Candidate Engine → 3-Card → Choice Log     │
└──────────────────────────────────────────────────────────────┘
                            ↓
                    선택 로그가 여행 내 학습으로 환류
```

**설계 원칙:** Prep은 Live를 위해서만 존재한다. Prep이 독립적으로 훌륭한 계획 도구가 되려는 순간, 제품은 트리플·Wanderlog와 같은 게임에 끌려 들어간다.

## Part 3. Feature Definitions

### Feature 1: Converter (변환기) — 제품의 진입점

사용자에게 새 노동을 요구하지 않는다. 이미 만든 준비물을 받는다.

#### 입력 소스

| 소스               | 파싱 방식                          | 우선순위 |
| ------------------ | ---------------------------------- | -------- |
| 구글맵 저장 리스트 | 공유 링크 → 장소 목록 추출         | **1순위** |
| AI 일정 초안       | 텍스트 붙여넣기 → 장소명 추출      | 1순위    |
| 블로그·유튜브 링크 | 본문에서 장소명 추출 (LLM)         | 2순위    |
| 인스타 저장        | 수동 입력 보조 (자동화 어려움)     | 3순위    |
| 트리플·노션 일정   | 텍스트 붙여넣기                    | 2순위    |

구글맵 저장 리스트가 1순위인 이유는, 한국 여행자의 사실상 표준 저장소이며 정형 데이터로 접근 가능하기 때문이다.

#### 변환 결과

40개 핀 → 조건 태그가 붙은 40개 플레이북 엔트리. 사용자가 할 일은 **확인과 우선순위 표시 2단계뿐**이다.

---

### Feature 2: Auto-Tagger (자동 태깅)

플레이북의 품질은 태깅 정확도가 결정한다. 태깅 부담을 사용자에게 넘기면 제품이 죽으므로, 자동화 수준과 신뢰도를 명시적으로 구분한다.

#### 태그 체계와 신뢰도 등급

| 등급     | 태그                                        | 획득 방식             | 사용 방식              |
| -------- | ------------------------------------------- | --------------------- | ---------------------- |
| **확정** | 좌표, 카테고리, 영업시간, 휴무일, 가격대    | 지도 API              | **하드 필터로 사용**   |
| **확정** | 실내 / 실외 / 혼합                          | 카테고리 규칙 매핑    | 하드 필터로 사용       |
| **추정** | 예상 소요시간                               | 카테고리 기준값 + 리뷰 | 소프트 필터            |
| **추정** | 활동 강도 (도보량)                          | 카테고리 + 면적       | 소프트 스코어          |
| **불확실** | 유아차·휠체어 접근성                      | 리뷰 텍스트 LLM 추출  | **표시만, 필터 금지**  |
| **불확실** | 대기 경향 (웨이팅 빈발)                   | 리뷰 텍스트 LLM 추출  | 표시만, 소프트 감점    |
| **사용자** | 우선순위 (필수 / 선택)                    | 원탭 2단계            | 소프트 스코어 상위     |
| **사용자** | 저장 이유 한 줄 (선택 입력)               | 자유 입력             | 현장 설명 문구로 재사용 |

**중요한 설계 판단:** 리뷰에서 LLM으로 추출한 접근성 정보는 **하드 필터로 쓰지 않는다.** "유아차 가능"이라고 단정했다가 현장에서 계단을 만나면 신뢰가 즉시 붕괴한다. 대신 `리뷰에 유아차 언급 있음`처럼 출처를 밝힌 표시로만 제공한다.

**우선순위를 2단계로 제한한 이유:** 필수/선택/대안 3단계 이상은 사용자가 끝까지 붙이지 않는다. 필수 표시는 전체의 10~20%만 붙어도 후보 선정에 충분히 작동한다.

#### 저장 이유 한 줄의 가치

선택 입력이지만 제품의 신뢰를 만드는 결정적 장치다. 현장에서 후보를 제시할 때 이 문장이 그대로 노출된다.

> "3주 전 저장 · *'비 오면 여기 가려고'* · 도보 6분"

과거의 자신이 미래의 자신에게 남긴 근거는 어떤 알고리즘 설명보다 설득력이 강하다.

### Feature 3: Playbook (플레이북) — 핵심 자산

시간이 아니라 조건으로 인덱싱된 옵션 세트다.

```
[플레이북 구조]

엔트리 = 장소/활동 + 확정 태그 + 추정 태그 + 사용자 태그

조회는 시간이 아니라 조건 조합으로 이루어진다:
  location(현재) × time(현재) × weather × remaining_time × state
      ↓
  하드 필터 → 소프트 스코어 → 다양성 제약 → 3개
```

플레이북에는 일정표가 존재하지 않는다. 다만 **확정된 예약(항공·숙소·예약 필수 스팟)** 은 별도로 고정 앵커로 보관되며, 이는 `남은 시간` 계산의 기준이 된다.

즉 시간 축은 완전히 사라지는 것이 아니라, **계획의 뼈대에서 조건 계산의 입력값으로 강등된다.**

---

### Feature 4: Context Sensor (조건 감지)

Live 모드가 질문하지 않으려면 조건을 스스로 알아야 한다.

| 조건        | 획득          | 오프라인 |
| ----------- | ------------- | -------- |
| 현재 위치   | GPS           | 가능     |
| 현재 시각   | 단말          | 가능     |
| 남은 시간   | 다음 앵커까지 자동 계산 | 가능 |
| 날씨        | API           | 불가 → 수동 칩 대체 |
| 실시간 혼잡 | API (선택)    | 불가 → 미사용 |
| 오늘 방문 이력 | 자체 로그  | 가능     |

사용자가 직접 알려줘야 하는 것은 **상태 칩 하나뿐**이며, 그마저도 선택이다.

```
[상태 칩 — 원탭, 복수 선택 가능, 안 눌러도 동작]
  지쳤음    배고픔    아이 잠듦    시간 애매    비 옴(오프라인 시)
```

칩을 누르지 않아도 위치·시각·날씨만으로 기본 3개가 나온다. **질문에 답해야 결과가 나오는 구조는 현장에서 실패한다.**

---

### Feature 5: Candidate Engine (후보 선정)

Live 모드의 로직 코어. v1은 학습 모델 없이 룰 기반으로 충분하다.

#### 1단계: 하드 필터 (탈락)

- 지금 영업 종료 / 오늘 휴무
- 도보 반경 초과 (기본 12분, `지쳤음` 시 7분, `아이 잠듦` 시 10분)
- 남은 시간 < 예상 소요시간
- 오늘 이미 방문

#### 2단계: 소프트 스코어 (순위)

| 신호                     | 가중 방향             |
| ------------------------ | --------------------- |
| 사용자 `필수` 표시       | 강한 가산             |
| 조건 적합 (비 → 실내)    | 강한 가산             |
| 거리 근접                | 가산                  |
| 오늘 같은 카테고리 방문  | **감점** (반복 회피)  |
| 대기 빈발 + `지쳤음`     | 감점                  |
| 저장 이유 존재           | 약한 가산 (의도 명확) |

#### 3단계: 다양성 제약

**3개가 모두 같은 카테고리이면 안 된다.** 최소 2개 카테고리를 강제한다. 카페 3개는 선택지가 아니라 그냥 목록이며, 동행과의 결정을 돕지 못한다.

#### 4단계: 폴백 (정직한 실패 처리)

| 상황                  | 처리                                                      |
| --------------------- | --------------------------------------------------------- |
| 플레이북 후보 3개 미만 | 지도 API 일반 결과로 보충하되 **`저장 안 한 곳`으로 명시 구분** |
| 후보 0개              | **"지금은 쉬는 게 낫다"** + 숙소 복귀 경로 안내           |

두 번째 폴백이 이 제품의 정체성을 지킨다. 억지로 뭔가를 제시하지 않는 것이 "쉬어라가 결론일 수 있어야 한다"는 원칙의 구현이다.

#### 왜 3개인가

2개는 선택지가 아니라 양자택일이라 동행 대화가 대립 구도가 된다. 5개 이상은 서 있는 상태에서 논의 마비를 만든다. **3개는 "이 중에 골라"라는 문장이 3초 안에 해결되는 최대 개수다.**

---

### Feature 6: Choice Log (선택 로그) — 데이터 모트

제시한 3개 중 **고른 것과 안 고른 것을 모두** 기록한다.

```json
{
  "trip_id": "...", "day_index": 2,
  "timestamp": "2026-10-14T15:20+09:00",
  "weather": "rain", "location": [34.70, 135.49],
  "state_chips": ["kid_asleep"],
  "remaining_minutes_est": 95,
  "presented": ["p_112", "p_087", "p_203"],
  "presented_reasons": ["실내·도보6분·저장이유있음", "...", "..."],
  "chosen": "p_087",
  "action": "chosen",
  "dwell_minutes": 47,
  "revisit_within_trip": false
}
```

이 로그의 가치는 18번 문서에서 정리한 대로다. 리뷰는 사후 진술이고 여행 1회당 1건 쌓이지만, 이 로그는 **모든 맥락 변수가 확정된 상태의 실제 선택**이며 여행 1회당 수십 건 쌓인다. OTA는 예약만, UGC는 진술만, 지도는 클릭만 갖는다.

---

### Feature 7: "다 별로" 루프

가장 중요한 학습 신호이므로 별도 기능으로 둔다.

```
[다 별로]  ← 항상 화면에 노출

누르면 즉시 이유 3개 원탭:
  너무 멀어    아까 비슷한 거 함    지금 그런 기분 아님

→ 즉시 다른 3개 제시 (질문 없이)
```

이 신호는 두 가지로 쓰인다. 단기적으로는 그 자리에서 재제시 조건을 바꾸고, 장기적으로는 조건 판정 규칙(반경 기본값, 카테고리 유사도, 강도 추정)의 보정 데이터가 된다.

**`다 별로` 비율이 높다는 것은 사용자 잘못이 아니라 태깅·필터의 실패**라는 관점을 지표 설계에 반영한다.

---

### Feature 8: 동행 공유 — 링크가 아니라 플레이북을 공유한다

현장 결정은 대부분 집단 결정이다. 그러나 현장에서 링크를 보내고 투표를 기다리는 비동기 방식은 실패한다. 같이 서 있는 사람들에게 메시징을 쓰게 만드는 설계이기 때문이다.

**해법: 플레이북 자체를 공유한다.**

동행이 같은 플레이북을 가지면 각자 Live를 열었을 때 **같은 3개**를 본다. 그러면 결정이 "이 중에 골라"라는 대면 대화 3초로 끝난다.

- 공유 단위: 플레이북 (여행 단위, 출발 전 1회)
- 현장 동기화: 위치·시각이 비슷하므로 자연히 같은 결과
- 필요 시: 한 명이 고르면 나머지에게 즉시 반영 (선택)

이는 트랩플랜·FlowTrip 등 협업 플래너와의 차별점이기도 하다. 그들은 편집 협업을 제공하고, 우리는 **현장 합의 비용**을 줄인다.

---

### Feature 9: Offline Degradation (오프라인 열화 동작)

로밍 불안정은 현장 제품의 구조적 리스크이므로 설계에 내장한다.

| 기능              | 온라인 | 오프라인                    |
| ----------------- | ------ | --------------------------- |
| 플레이북 조회     | O      | **O** (출발 전 캐시)        |
| 위치·시각·거리    | O      | **O**                       |
| 영업시간·휴무 판정 | O     | **O** (캐시된 정적 정보)    |
| 날씨 자동 감지    | O      | X → 수동 칩(`비 옴`)으로 대체 |
| 실시간 혼잡·대기  | O      | X → 미사용                  |
| 폴백 일반 검색    | O      | X → 플레이북 내에서만       |

**핵심 기능은 전부 오프라인에서 동작해야 한다.** 이 요구사항은 16 문서의 "웹 우선" 결론을 재검토하게 만든다. Prep 모드는 웹으로 충분하지만, **Live 모드는 앱 또는 강력한 PWA 캐시가 필요하다.**

## Part 4. MVP Build Order

### Sprint 1-2: Converter

- 구글맵 저장 리스트 링크 파싱
- 텍스트 붙여넣기 파서 (AI 초안 / 일정표)
- 지도 API 연동, 확정 태그 자동 부여
- 변환 결과 확인 UI (일괄 확인, 개별 수정)

**이 단계까지가 단독으로 유입 가치를 가진다.** "저장 리스트 정리해 드립니다."

### Sprint 3-4: Playbook + Offline

- 추정 태그 파이프라인 (소요시간·강도)
- 우선순위 원탭 2단계, 저장 이유 입력
- 고정 앵커(숙소·예약) 등록
- 오프라인 캐시 구조

### Sprint 5-6: Live Mode v1 — 핵심 검증 구간

- Context Sensor (위치·시각·날씨·남은 시간)
- 상태 칩
- Candidate Engine (하드 필터 → 소프트 스코어 → 다양성 → 폴백)
- 3-Card 화면, 제시 이유 노출
- **이 스프린트 종료 시점에 핵심 가설(구글맵 이탈률)을 측정한다**

### Sprint 7-8: Learning Loop

- Choice Log 수집
- `다 별로` 루프
- 여행 내 학습 (2일차가 1일차를 반영)
- 체류시간 추정

### Sprint 9+

- 동행 플레이북 공유
- in-destination 예약 연결 (판단 영역과 분리)
- 도시 확장 (방콕·다낭 — 차량 이동 가설 재검증 필요)
- 여행 후 요약 (선택 로그 기반 자동 생성)

## Part 5. Guardrails

### Guardrail 1: 현장 화면은 스크롤 없이 답이 보여야 한다

서 있는 사람이 한 눈에 읽을 수 있는 분량만. 스크롤이 필요하면 이미 실패다.

### Guardrail 2: 질문하지 않는다

Live 모드를 열면 이미 답이 있어야 한다. 상태 칩은 결과를 좁히는 선택 장치이지 진입 조건이 아니다.

### Guardrail 3: "쉬어라"와 무료 옵션이 항상 가능해야 한다

후보 0개일 때 억지 제시를 하지 않는다. 이 원칙이 무너지면 GetYourGuide가 된다.

### Guardrail 4: 내 것과 남의 것을 구분한다

플레이북 후보와 일반 검색 폴백을 시각적으로 명확히 구분한다. 신뢰의 원천이 "내가 저장한 것"이기 때문이다.

### Guardrail 5: 제시에는 항상 한 줄 이유가 붙는다

"실내 · 도보 6분 · 3주 전 저장('비 오면 여기')". 이유 없는 3개는 구글맵과 구별되지 않는다.

### Guardrail 6: 불확실한 태그로 단정하지 않는다

접근성·대기 정보는 출처를 밝힌 표시로만. 하드 필터 금지.

### Guardrail 7: 오프라인에서 열화 동작한다

핵심 조회는 네트워크 없이 성립해야 한다.

## Part 6. Final Build Logic

```
Import first
→ 이미 만든 준비물을 가져온다 (새 노동 요구 금지)

Tag automatically
→ 확정/추정/불확실을 구분해 자동 태깅

Index by condition
→ 시간이 아니라 조건으로 묶는다 (이탈에 강한 구조)

Sense silently
→ 현장 조건을 스스로 감지한다 (질문 금지)

Retrieve in three
→ 조건에 맞는 3개, 이유와 함께

Log everything
→ 고른 것과 안 고른 것 모두 (데이터 모트)

Learn within the trip
→ 여행 간 학습보다 여행 내 학습이 먼저 (저빈도 대응)
```

이 순서가 깨지면, 특히 첫 번째(Import)가 "우리 앱에서 계획하세요"로 바뀌는 순간, 제품은 다시 평범한 여행 플래너가 된다.
