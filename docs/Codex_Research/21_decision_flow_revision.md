## 1. 문서명 결론

이 문서의 파일명은 **`21_decision_flow_revision.md`**가 가장 적절하다.

이유:

- 바뀌는 포인트가 `유입`, `Priority 순서`, `카테고리 진입 방식`, `화면 통합`에 집중되어 있다.
- 따라서 `wireframe`보다 `flow revision`이 더 정확하다.

즉, 이 문서는 **19_wireframe의 후속 수정안**으로 보는 것이 맞다.

## 2. 이번 수정의 핵심 결론

네가 지적한 4가지는 모두 타당하다.  
그리고 단순 부분 수정이 아니라 **MVP 흐름의 중심축을 조금 바꾸는 수준의 수정**이 필요하다.

최종 결론은 아래와 같다.

1. **특정 제품군을 생각하고 들어온 사용자를 위한 fast lane이 필요하다**
2. **Priority가 Skin Profile보다 먼저 와야 한다**
3. **초기 Priority는 "모든 걸 다 묻는 진단형"이 아니라, "제품 사기 전 먼저 볼 것" 중심의 gate여야 한다**
4. **기존 6번 Category Decision과 7번 Product List/Compare는 하나의 화면으로 통합하는 것이 맞다**

즉, 기존 19번 문서의 흐름은 아래처럼 수정되는 것이 자연스럽다.

```text
기존
랜딩 -> 세그먼트 -> Skin Profile -> Routine Baseline -> Priority Result -> Category Decision -> Product Compare -> Product Fit -> Traceback

수정안
랜딩 -> 진입 분기 -> Priority Gate -> Minimal Context -> Decision Result -> Category Decision Matrix -> Product Fit -> Traceback/Tracker
```

## 3. 이슈 1: "썬크림 골라주세요"처럼 특정 제품군을 생각하고 들어온 사람

## 3-1. 기존 구조의 문제

기존 구조는 `어디서부터 손댈지 모름 -> 문제는 있는데 카테고리 모름 -> 이미 카테고리를 생각함`으로 잘 나뉘어 있지만,  
실제 검색 유입에서는 아래처럼 들어오는 사용자가 많다.

- `썬크림 골라주세요`
- `민감성 립밤 추천`
- `장벽크림 뭐가 좋아요`
- `비타민C 세럼 추천`

이 사용자는 이미 제품군을 생각하고 있다.  
그런데 바로 제품 비교로 보내면 기존 커머스/랭킹 서비스와 다를 게 없다.

문제는 여기서 생긴다.

- 사용자는 카테고리를 이미 정했지만, **그 카테고리가 지금 진짜 필요한지**는 아직 검증되지 않았다.
- 그래서 `카테고리 진입은 빠르게`, `제품 추천은 늦게` 가야 한다.

---

## 3-2. 결론

**"특정 제품군 진입형 fast lane"을 따로 두는 것이 맞다.**

다만 이 fast lane은 곧바로 제품 리스트로 보내는 길이 아니라,

> **Category preset -> Priority Gate -> Minimal Context -> Category Decision Matrix**

로 이어져야 한다.

즉, "선크림 보러 온 사람"도 먼저 아래를 확인해야 한다.

- 정말 제품 교체가 필요한가
- 기존 루틴이 먼저 문제인가
- 이 카테고리에서 어떤 기준이 중요한가

---

## 3-3. 추천 UX 구조

### Entry 방식

진입 버튼은 아래 4개를 유지하되, 3번을 더 명확하게 바꾼다.

1. 어디서부터 손대야 할지 모르겠어요
2. 고민은 있는데 어떤 카테고리인지 모르겠어요
3. **이미 찾는 제품군이 있어요**
4. 예전에 안 맞았던 제품 원인을 알고 싶어요

3번을 누르면 바로 카테고리 preset을 받는다.

예:

- 선크림
- 세럼
- 장벽 크림
- 클렌저
- 립 케어
- 토너패드

---

## 3-4. "선크림 골라주세요" 유입의 실제 흐름

```text
검색 유입: 선크림 골라주세요
-> 카테고리 preset: 선크림
-> Priority Gate
   -> 선크림을 안 바르거나 재도포를 거의 안 함: 루틴 먼저
   -> 선크림은 쓰지만 눈시림/백탁/밀림이 문제: 제품 탐색 계속
-> Minimal Context
-> Decision Result
-> Category Decision Matrix
-> Product Fit Detail
```

이게 좋은 이유:

- 특정 제품군 유입을 놓치지 않는다.
- 그래도 `무조건 제품 추천`으로 무너지지 않는다.
- "선크림을 뭘 살까?"를 "지금 선크림에서 뭘 봐야 하나?"로 바꿀 수 있다.

## 4. 이슈 2: 3, 4번 순서 변경

## 4-1. 기존 구조

기존 19번 문서는 아래 순서였다.

3. Skin Profile 입력
4. Routine Baseline 입력
5. Priority Result

이 구조는 논리적으로 깔끔하지만, 실제 유입에서는 약점이 있다.

- 사용자가 아직 "제품이 필요한지"도 모르는 상태에서 피부 타입부터 묻게 된다.
- 질문이 많아 보인다.
- 특정 제품군 유입 사용자에게는 진입 저항이 생긴다.

즉, **진입 초반의 질문이 너무 개인화 중심**이다.

---

## 4-2. 수정 결론

**Priority가 먼저 와야 한다.**

순서는 아래처럼 바꾸는 것이 맞다.

1. 랜딩
2. 진입 분기
3. **Priority Gate**
4. **Minimal Context 입력**
5. Decision Result

이 변경의 의미는 크다.

- 먼저 `지금 제품을 사야 하는가?`를 판별한다.
- 그다음에야 `무슨 피부인지, 민감한지, 액티브를 쓰는지`를 묻는다.

즉, **개인화는 구매 필요성 판별 이후에 붙는 보정 레이어**가 된다.

---

## 4-3. Skin Profile의 역할도 바뀌어야 한다

기존에는 Skin Profile이 초반 핵심 입력이었다면,  
수정안에서는 아래 역할로 내려오는 것이 맞다.

> **"추천을 만들기 위한 기본 설문"이 아니라, "Priority 통과 후 후보를 줄이기 위한 필터"**

따라서 Skin Profile은 필수 입력을 최소화하고, 아래 정도만 남기는 것이 적절하다.

- 민감도
- 현재 사용 중 액티브
- 피부 타입 또는 자기 인식 피부 상태
- 제형 선호
- 예산대

여기서 중요한 점:

- 피부 타입은 **초기 절대 필수값이 아니다**
- 오히려 `민감도`, `현재 액티브`, `문제 부위`, `사용 상황`이 더 먼저일 수 있다

## 5. 이슈 3: Priority는 어떻게 바꿔야 하는가

## 5-1. 비교 대상

Priority에는 현재 두 가지 버전이 있다.

### A. 초기 구상

루틴 / 생활방식 / 피부관리 상식 / 화장품 / 행동 우선순위를 전부 포괄하는 넓은 개념

### B. 현재 예시

`제품을 사기 전에 먼저 확인하세요`라는 성격의 구매 전 체크리스트

예시:

- 매일 선크림을 바르고 있다
- 세안 후 당김이 심하지 않다
- 보습제를 꾸준히 바른다
- 최근 강한 필링/레티놀/홈케어를 하지 않았다
- 수면 부족/야식/과식이 심하지 않다
- 화장품을 최근 여러 개 바꾸지 않았다
- 같은 문제가 2~4주 이상 반복된다
- 피부과 상담을 고려할 정도로 스트레스가 크다

---

## 5-2. 비교

| 항목 | 초기 넓은 Priority                             | 현재 체크리스트형 Priority                       |
| ---- | ---------------------------------------------- | ------------------------------------------------ |
| 장점 | 서비스 철학을 잘 담음                          | 빠르고 실전적임                                  |
| 장점 | 루틴/생활/행동까지 넓게 다룸                   | 특정 제품군 유입에도 바로 적용 가능              |
| 장점 | 결과 설명의 깊이를 만들기 좋음                 | "지금 사지 말아야 할 것"을 설득하기 좋음         |
| 단점 | 초반 입력이 길고 무거워짐                      | 이것만으로는 개인화가 부족함                     |
| 단점 | 진단형 설문처럼 느껴질 수 있음                 | 카테고리별 세부 맥락이 빠질 수 있음              |
| 단점 | 제품군 intent가 강한 사용자에게 답답할 수 있음 | 일부 문항은 모든 카테고리에 공통 적용하기 어려움 |

---

## 5-3. 결정

**현재 체크리스트형 Priority를 메인으로 쓰는 것이 맞다.**  
대신 초기의 넓은 Priority 개념은 버리는 것이 아니라, 아래처럼 쪼개서 흡수해야 한다.

### Layer A. Priority Gate

진입 초반에 쓰는 짧은 체크리스트  
목적: `지금 제품을 사야 하는가 / 무엇을 먼저 해야 하는가`

### Layer B. Context Deepening

Priority 통과 후 받는 맥락 입력  
목적: `후보를 줄이고, 제품 적합도를 정교화`

### Layer C. Result Explanation

결과 화면에서 보여주는 생활/루틴/관리 우선순위 설명  
목적: `왜 이게 먼저고 왜 이건 보류인지 설명`

즉, 초기의 넓은 Priority 철학은 살아 있어야 한다.  
하지만 **첫 화면 설문 자체는 짧고 명확한 gate형이어야 한다.**

## 5-4. 지금 예시 체크리스트에서 수정할 점

현재 예시는 방향이 좋다.  
다만 아래 두 가지는 조정하는 것이 더 좋다.

### 1. `매일 선크림을 바르고 있다`

이 문항은 중요하지만, 모든 사용자에게 같은 비중으로 던지면 다소 선크림 편향적으로 보일 수 있다.

따라서 아래처럼 쓰는 편이 더 좋다.

- **공통 문항:** 기본 보호/보습 루틴이 안정적이다
- **고민/카테고리 조건부 문항:** 색소/노화/주간 노출 고민이면 `매일 선크림을 바르고 있다`

즉, `선크림 문항`은 매우 중요하지만 **조건부 핵심 문항**으로 다루는 것이 맞다.

### 2. `수면 부족/야식/과식이 심하지 않다`

이 문항은 방향은 맞지만 표현이 너무 구체적이고 단정적이다.

더 좋은 문구는 아래다.

- 최근 수면/스트레스/식습관 변화가 크지 않다

이렇게 바꾸면:

- 과학적 과장처럼 보이지 않는다
- 특정 음식과 피부 문제를 과도하게 단순화하지 않는다
- 법적/의학적 리스크도 줄어든다

---

## 5-5. 최종 권장 Priority 구조

### 공통 Priority Gate

1. 최근 기본 보습/보호 루틴이 불안정하다
2. 세안 후 당김/자극이 자주 있다
3. 최근 강한 액티브/필링/홈케어를 했다
4. 최근 여러 화장품을 한꺼번에 바꿨다
5. 같은 문제가 2~4주 이상 반복된다
6. 최근 수면/스트레스/식습관 변화가 크다
7. 이 문제로 일상 스트레스가 크거나 상담이 필요하다고 느낀다

### 조건부 Priority 문항

#### 색소/잡티/노화/선케어 관심

- 매일 선크림을 바르고 있다
- 외출 시 재도포가 가능하다

#### 메이크업 밀림/베이스 문제

- 아침 루틴이 너무 무겁지 않다
- 스킨케어 후 바로 화장을 하지 않는다

#### 여드름/트러블

- 최근 마찰/운동/땀/세정 과다 요인이 크지 않다
- 최근 강한 패드/필링/레티노이드 사용이 과하지 않았다

즉, Priority는 **공통 gate + 문제별 보정 질문** 구조가 가장 좋다.

## 6. 이슈 4: 6번과 7번 화면 통합

## 6-1. 기존 구조

기존 19번 문서:

6. Category Decision
7. Product List / Compare

이 구조는 논리적으로는 분리되어 있지만, 실제 사용 흐름에서는 끊김이 생길 수 있다.

- 6번에서 선택 기준을 읽고
- 7번으로 넘어가서 다시 제품을 봐야 한다

이렇게 되면 사용자가 `선택 기준`과 `제품 후보`를 머릿속에서 따로 연결해야 한다.

---

## 6-2. 결론

**6번과 7번은 통합하는 것이 맞다.**

이 통합 화면의 핵심은 아래다.

> **"이 카테고리에서 중요한 선택 기준"과 "지금까지 정보로 필터링된 제품 라인"을 한 화면에서 같이 보여준다**

즉, 새 화면은 단순 제품 리스트가 아니라  
**Category Decision Matrix** 또는 **Category Decision + Product Matrix**가 된다.

---

## 6-3. 통합 화면 구조

### 상단

- 현재 문제 요약
- Priority 결과 요약
- 보류/주의 배지
- 현재 카테고리명

### 중단 왼쪽 또는 상단 블록

- 이 카테고리에서 중요한 선택 기준
- Good fit / Skip if
- 제형/사용감 기준
- 상황별 핵심 포인트

### 중단 오른쪽 또는 하단 메인

- 지금까지 정보로 필터링된 Product Matrix
- 가격대별 라인
- 사용감/제형별 라인
- 적합도/주의 태그
- 비교 추가

### 하단

- Product Fit Detail 진입 CTA
- 후보 저장
- 지금은 보류하기

---

## 6-4. 이 통합안의 장점

1. 사용자가 `무엇을 봐야 하는지`와 `무엇을 고를 수 있는지`를 한 번에 이해한다
2. 화면 하나를 줄일 수 있다
3. 가격대별 제품 라인 탐색이 자연스럽다
4. 기존 커머스식 리스트보다 `판단 기준이 먼저 보이는 제품 비교`가 된다

즉, 네가 말한 방향이 맞다.  
**필요 제품군을 선정한 뒤, 그 카테고리의 선택 기준과 필터링된 제품 매트릭스를 한 화면에서 보는 구조가 더 좋다.**

## 7. 수정 후 최종 화면 구조

## 7-1. 코어 화면 수

기존 9개 코어 화면에서,  
6번과 7번 통합으로 **실질 코어 8개 화면**으로 정리할 수 있다.

### 수정 후 코어 화면

1. 랜딩 / Intent Entry
2. 진입 분기 / 세그먼트 선택
3. Priority Gate
4. Minimal Context 입력
5. Decision Result
6. Category Decision Matrix
7. Product Fit Detail
8. Reaction Traceback / Adaptation Tracker

### 선택 화면

9. 저장 / 로그인
10. 내 기록 보기
11. 공유 결과 페이지

---

## 7-2. 각 화면의 역할

### 1. 랜딩 / Intent Entry

- 서비스 한 문장 설명
- 고민 예시
- 검색형 진입 CTA
- 제품군 직접 진입 CTA

### 2. 진입 분기 / 세그먼트 선택

- 어디서부터 손댈지 모름
- 고민은 있는데 카테고리를 모름
- 이미 찾는 제품군이 있음
- 안 맞았던 제품 원인을 알고 싶음

### 3. Priority Gate

- 제품이 지금 필요한가
- 루틴/생활/자극 요인이 먼저인가
- 상담 고려가 필요한가

### 4. Minimal Context 입력

- 민감도
- 현재 액티브
- 피부 타입 또는 현재 피부 상태
- 제형 선호
- 예산대

### 5. Decision Result

- 지금 먼저 할 것
- 지금 보류할 것
- 추천 카테고리
- 다음 액션

### 6. Category Decision Matrix

- 카테고리 선택 기준
- 필터링된 Product Matrix
- 가격대별 라인
- 비교 진입

### 7. Product Fit Detail

- 적합 / 주의 / 회피
- 이유 설명
- 유사 피부 evidence
- 사용 순서와 빈도

### 8. Reaction Traceback / Adaptation Tracker

- 실패 원인 후보 추적
- 사용 후 Day 3 / 7 / 21 체크인

## 8. 실제 사용자 흐름 예시

## 예시 1. 선크림을 생각하고 들어온 사람

```text
랜딩
-> 이미 찾는 제품군이 있어요
-> 선크림 선택
-> Priority Gate
   -> 선크림 사용 자체가 불안정하면: 루틴 먼저
   -> 사용은 하는데 눈시림/밀림이 문제면: 계속 진행
-> Minimal Context
-> Decision Result
-> Category Decision Matrix
-> Product Fit Detail
```

-> Priority Gate

   -> 지금은 장벽 회복과 선케어가 먼저
-> Category Decision Matrix

```

-> Reaction Traceback

-> 이후 Category Decision Matrix로 연결 가능
```

## 9. 최종 판단

네가 지적한 4가지는 모두 반영하는 것이 맞다.  
특히 중요한 것은 아래 두 가지다.

1. **Priority를 앞당겨서 "제품이 필요한지"를 먼저 판단하게 할 것**
2. **Category Decision과 Product Matrix를 한 화면으로 붙일 것**

이 두 가지가 반영되면 서비스는 더 이상  
`설문 -> 추천` 구조가 아니라,

> **"필요성 점검 -> 맥락 보정 -> 선택 기준 제시 -> 필터링된 제품 비교"**

구조가 된다.

이게 지금 이 서비스에 더 맞다.
